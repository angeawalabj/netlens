# Jour 19 — Load balancing et haute disponibilité

## La situation réelle

Votre service reçoit 10 000 requêtes par seconde. Un seul serveur ne suffit plus. Comment répartir la charge sur plusieurs serveurs et garantir qu'une panne d'un serveur ne coupe pas le service ?

---

## Load balancers — répartir la charge

Un load balancer distribue les requêtes entrantes vers un pool de serveurs (backends).

### Algorithmes de répartition

**Round-robin :** chaque serveur reçoit les requêtes à tour de rôle. Simple, efficace si les serveurs sont identiques.

**Least connections :** envoie vers le serveur ayant le moins de connexions actives. Mieux pour des requêtes à durée variable.

**IP Hash :** même IP client → même serveur. Utile pour la persistance de session (sessions "sticky").

**Weighted :** les serveurs puissants reçoivent proportionnellement plus de requêtes.

### Layer 4 vs Layer 7

**L4 (TCP/UDP) :** le LB ne voit pas le contenu HTTP. Très rapide, mais pas de routage basé sur l'URL.

```
TCP:443 → serveur1:443 (round-robin)
TCP:443 → serveur2:443
```

**L7 (HTTP) :** le LB termine les connexions TLS, lit les en-têtes HTTP, et route intelligemment.

```
GET /api/*  → api-servers
GET /static/* → cdn-origin
GET /admin/* → admin-server (+ auth check)
```

### nginx comme reverse proxy / load balancer

```nginx
upstream backend {
    least_conn;                     # algorithme
    server backend1.example.com:8080;
    server backend2.example.com:8080;
    server backend3.example.com:8080 weight=2;  # 2x plus de trafic
    keepalive 32;                   # connexions persistantes
}

server {
    listen 443 ssl http2;
    ssl_certificate /etc/ssl/cert.pem;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## Health checks — détecter les pannes

Le LB doit savoir quels backends sont opérationnels.

```nginx
upstream backend {
    server backend1.example.com:8080;
    server backend2.example.com:8080;

    # nginx Plus / OpenResty
    check interval=3000 rise=2 fall=3 timeout=1000 type=http;
    check_http_send "GET /health HTTP/1.0\r\n\r\n";
    check_http_expect_alive http_2xx;
}
```

**Endpoint de health check recommandé :**
```
GET /health
→ 200 OK si tout va bien
→ 503 si la DB est inaccessible ou le service dégradé
```

## Haute disponibilité — éliminer les SPOF

**SPOF (Single Point of Failure)** : un composant dont la panne coupe tout le service.

**keepalived + VIP :** deux load balancers partagent une IP virtuelle (VIP). Si le primaire tombe, le secondaire prend la VIP via VRRP.

```bash
# /etc/keepalived/keepalived.conf (primaire)
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100            # plus élevé = primaire
    virtual_ipaddress {
        192.168.1.100       # VIP
    }
}
```

**DNS round-robin :** plusieurs A records pour le même domaine. Simple mais pas de failover automatique (le TTL cache les IPs même si un serveur est down).

**Anycast :** la même IP est annoncée depuis plusieurs datacenters via BGP. Le routage réseau envoie vers le plus proche. Si un DC tombe, le routage change automatiquement.

---

## À retenir

- Load balancer L4 = TCP/UDP, pas d'inspection du contenu, très rapide
- Load balancer L7 = HTTP, routing intelligent, termine TLS
- Round-robin, least-conn, IP hash, weighted = algorithmes de distribution
- Health checks = détecter les backends down automatiquement
- VIP + keepalived = haute disponibilité du load balancer lui-même
- Anycast = disponibilité géographique via BGP
