# Jour 22 — CDN et optimisation de la livraison

## La situation réelle

Votre application est hébergée à Paris. Un utilisateur au Japon reçoit vos fichiers avec 200ms de latence (RTT Paris-Tokyo). Comment servir vos assets en <20ms depuis n'importe où dans le monde ?

---

## CDN — Content Delivery Network

Un CDN est un réseau mondial de serveurs cache (Points of Presence — PoP) qui servent le contenu depuis la localisation géographiquement la plus proche de l'utilisateur.

```
Utilisateur Tokyo    → PoP Tokyo   (20ms) ← contenu mis en cache
Utilisateur Paris    → PoP Paris   (5ms)  ← contenu mis en cache
Utilisateur New York → PoP New York (15ms) ← contenu mis en cache
                         ↑
              Tous populés depuis votre Origin (Paris)
```

### Fonctionnement

1. L'utilisateur résout `cdn.example.com` via DNS
2. Le DNS du CDN (via GeoDNS ou Anycast) retourne l'IP du PoP le plus proche
3. Si le PoP a le contenu en cache → réponse immédiate
4. Sinon → cache miss → PoP récupère depuis l'Origin → met en cache → sert

---

## Cache-Control et CDN

Les CDN respectent les headers HTTP pour décider ce qui est cacheable :

```
Cache-Control: public, max-age=31536000, immutable
# → CDN cache 1 an, jamais revalidé (fichiers versionnés)

Cache-Control: public, max-age=3600, s-maxage=86400
# → navigateur: 1h | CDN: 24h

Cache-Control: private, no-store
# → ni navigateur ni CDN ne cachent (données sensibles)

Surrogate-Control: max-age=604800
# → header CDN-spécifique (Fastly, Varnish) ignoré par navigateur
```

### Versioning des assets

Pour profiter de `max-age=31536000` sans problème de cache :

```html
<!-- ❌ Mauvais — le navigateur cache, puis ignores les mises à jour -->
<script src="/app.js"></script>

<!-- ✓ Bien — hash dans le nom → nouvelle URL = nouveau fichier -->
<script src="/app.a3f4c8d2.js"></script>
```

Votre build tool (webpack, vite) gère ça automatiquement.

---

## CDN et TLS

Les CDN terminent le TLS : la connexion TLS est entre l'utilisateur et le PoP CDN (proche), pas entre l'utilisateur et votre origin (loin). Ça réduit la latence de négociation TLS de 200ms à 10-20ms.

```
Utilisateur ←──TLS──► PoP CDN (Tokyo, 10ms)
                          │
                     PoP CDN ←──TLS──► Origin (Paris, 200ms)
                     (connexion persistante, réutilisée)
```

---

## Invalidation de cache

Quand vous déployez, vous devez invalider les caches CDN pour le contenu non-versionné (HTML, API responses).

```bash
# Cloudflare
curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"files":["https://example.com/","https://example.com/index.html"]}'

# AWS CloudFront
aws cloudfront create-invalidation \
  --distribution-id $DIST_ID \
  --paths "/*"
```

## Providers CDN courants

| CDN | Force | Usage typique |
|-----|-------|---------------|
| Cloudflare | Sécurité + perf, DDoS, gratuit | Sites web, API |
| AWS CloudFront | Intégration AWS | Apps AWS |
| Fastly | Faible latence, VCL flexible | Médias, streaming |
| Akamai | Réseau le plus étendu | Enterprise |
| Bunny.net | Rapport qualité/prix | Startups |

---

## À retenir

- CDN = cache géographiquement distribué, réduit la latence et la charge Origin
- Cache miss = PoP va chercher à l'Origin, met en cache, sert
- Versionner les assets = cache long sans problème de mise à jour
- CDN termine TLS → latence de handshake réduite
- Invalider le cache après deploy pour le contenu non-versionné
